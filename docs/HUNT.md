# Ghost Hunt: bounded adversarial policy testing

Ghost Trials now uses the existing trial queue, simulator worker, evidence repository, and judge to run a bounded Hunt against one configured Unitree G1 policy. The primary workflow is **Release the Ghost → observe trials → inspect verified failures → replay or regress against a new checkpoint**. This is experimental policy evaluation, not safety certification.

## What actually runs

`POST /hunts` accepts the backend's executable task/environment, supported hazard family, trial budget (3–50), and optional strategy/search space. SONIC currently supports `walk forward 1m` in the configured MuJoCo scene; Arena uses its configured Galileo G1 pick-and-place scene. Arbitrary task text or scene selection is rejected until the worker can execute it. The server pins the policy and embodiment to the configured worker; clients cannot choose arbitrary checkpoint paths. Each candidate is admitted through the same job quota and paid-budget controls as a manual trial. It gets a deterministic seed and a versioned `execution_recipe`. After Cosmos/local generation, the planned recipe is validated against the generated hazard type before the simulator executes. The generated Cosmos video is illustrative; the simulator recording and telemetry are the evidence source.

Supported controls reflect executable worker knobs, not hypothetical sliders:

| Hazard | Backend | Bounded controls |
|---|---|---|
| Falling object / path obstruction | SONIC/MuJoCo or Isaac Arena | onset time, obstacle forward/lateral offset, obstacle forward speed, object mass |
| Reduced traction | SONIC/MuJoCo only | onset time, whole-floor friction coefficient |

The SONIC scene now uses the recipe's object mass. Arena already configures object mass from the recipe. Unsupported parameters, out-of-bounds values, and invalid hazard/backend combinations are rejected before a worker job is accepted. Friction and box hazards remain separate; the current simulator does not claim to test their combination.

Adaptive search starts with broad seeded exploration, then repeats observed failures with the exact saved scenario, probes a conditional boundary, and mutates nearby controls within bounds. Random and grid strategies remain available for baseline experiments. The trial budget includes reproductions and provider failures. The search cannot establish a global worst case or a universal safe threshold. An empirical boundary is reported only for observed pass/fail pairs with the same seed and all other controls held constant.

Observations are calculated from retained trial metrics: recorded fall/collision or task noncompletion is a failure; low clearance/contact slip can be a near-failure. Nemotron's interpretation is stored separately. A provider error is not a policy failure. A Ghost Case is created only when the existing independent artifact and metric checks pass and the full evidence report is complete. Synthetic/local trials can exercise the Hunt workflow but **cannot create production Ghost Cases**. Neither artifact hashes nor video decode are hardware attestation.

`GET /hunts/{id}` returns all candidates and observations. `GET /ghost-cases/{id}` returns the saved recipe, seed, policy/checkpoint digest, simulator version, metric record, video/telemetry links, artifact manifest, verification, and reproduction history. An explicit `POST /hunts/{id}/resume` is required after interruption; potentially billable work is never silently retried after restart. A compatible new checkpoint can be served on the same worker and submitted via `POST /ghost-cases/{id}/regressions`. The comparison requires the same scenario, recipe, embodiment, simulator version, metric basis, rubric, and independently checked evidence. “Fixed on case” means only that this candidate passed this tested case.

`GET /failure-families` groups saved cases deterministically by hazard type, executable task, observed failure mode, and checkpoint digest. This is a navigation aid, not learned clustering or a causal diagnosis.

## Honest readiness status

The local test suite uses synthetic fixtures for search-algorithm and API tests. Those are not evidence of GPU execution. A genuine end-to-end Hunt still requires a compatible, pinned G1 policy checkpoint, an available GPU worker running SONIC or Arena, live Cosmos/Nemotron access, and an actual captured worker trial. In production, missing resources block execution; there is no synthetic fallback.

## Live-run handoff (not yet executed)

1. Put a provider-issued NVIDIA API Catalog key in the **backend's private** `NVIDIA_API_KEY`. Hosted Cosmos3 Nano uses `COSMOS_API_STYLE=nvidia_catalog`, an empty `COSMOS_BASE_URL`, and 25 frames for the first connection test. The production template has these non-secret settings; it does not create a key or make a paid call. [NVIDIA's model card](https://build.nvidia.com/nvidia/cosmos3-nano/modelcard) documents the text-to-video request. Generated video is illustrative, not robot telemetry.
2. Agree a maximum **total** spend and per-trial reservation with the account owner. Set any available provider-side billing caps/alerts in the Nebius and NVIDIA consoles and a VM auto-shutdown policy. Then set `GHOST_PLATFORM_BUDGET_CENTS`, `GHOST_LIVE_JOB_RESERVATION_CENTS`, and organization budget to the approved values. App reservations are admission accounting, **not** provider billing caps. Do not set `GHOST_PROVIDER_SPENDING_CONTROLS_CONFIRMED=true` or `GHOST_LIVE_EXECUTION_ENABLED=true` until the external controls and resources are actually confirmed. Run `.venv/bin/python -m ghost_trials.live_hunt_preflight --max-trials 3`; it makes no API calls and prints no secrets. A green result is configuration readiness only, not live execution proof or independent verification of a provider cap.
3. Pin a compatible `unitree_g1_sonic` checkpoint and digest, bring up the authenticated GPU worker, and pass the read-only `ghost_trials.gpu_acceptance` check. Enable the paid gates only after the above conditions. In the authenticated Hunt screen, choose the supported task/environment, start a **three-trial** Hunt, and watch each trial reach a terminal state. A provider error or missing evidence blocks the Hunt; it is not a policy failure. Check the actual response MP4 and telemetry of every putative failure before calling it a finding.
4. Export the worker evidence bundle for the selected trial and run `ghost_trials.independent_validation` using a checkpoint digest obtained **independently** from the deployed package. Have a robotics reviewer play the full MP4, inspect the raw trace, onset alignment, control/action mapping, task validity, sensor limitations, and measured failure. Obtain the reviewer's own label and rationale; `ghost_trials.review_audit` compares that supplied label to the model finding. Neither a passing hash check nor a reviewer name entered by the developer proves independent attestation.
5. Open the resulting Ghost Case and inspect its saved recipe, seed, simulator version, evidence manifest, and reproduction status. Serve a **different compatible** checkpoint on the same backend, configure its new digest, and submit the case regression. The result can establish “fixed on this case” only if the candidate evidence validates and cohort compatibility checks pass. Then release a new Hunt against that checkpoint to search for new failures.
6. Film the real UI, Cosmos generation, worker simulation, telemetry/verification, model finding, and exact regression outcome. Identify whether the recorded backend was SONIC/MuJoCo or Isaac Arena. Follow the [demo script](submission/DEMO_SCRIPT.md) and update every claim in the submission to match the observed run. A demo video cannot be responsibly recorded as a genuine GPU trial until this run exists.
